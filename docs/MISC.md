# MISC 杂项记录

> 记录不属于功能变更、但值得保留的方案取舍与非功能性观察。

## 2026-07-29 原生 Android 与跨端视觉取舍

- **Android 是独立客户端，不是 WebView。** 用户明确要求原生 App 后，原先
  “第一阶段只做 PWA”的边界结束；`apps/android` 直接消费 Gateway 读 API，但仍
  复用五类 Session、等待优先和设备筛选语义，不能演化成第二套产品分类。
- **视觉一致不等于布局逐像素一致。** 三端共享 Paper/Ink/Muted/Line/Pink Signal、
  字重、圆角和组件语法；桌面保留双栏效率，PWA 保留浏览器模态，Android 使用系统
  Back 和原生页面栈。
- **原生凭据不能照搬 Web 的服务端代理。** Android 必须直连 Gateway，因此生产只
  接受 HTTPS，Bearer 令牌使用不可导出的 Keystore AES-GCM 密钥加密；回环开发用户
  只为 `adb reverse` 调试保留。
- **首版先闭合只读主路径。** 设备、Session、详情、时间线和前台刷新已落地；原生
  推送、后台任务、离线快照与商店签名单独验收，不能用浏览器 Push 或 debug APK
  替代。

## 2026-07-29 移动端 UI 第五轮取舍

- **同一个详情在手机是模态、桌面是侧栏。** 组件继续共享同一数据和时间线，只用
  `matchMedia(max-width: 919px)` 控制模态副作用与 ARIA；手机锁滚动、圈焦点，
  桌面允许用户继续操作列表和筛选，不能把两种交互一刀切。
- **相邻导航服从当前可见列表。** 上一条/下一条使用已排序、已应用设备和分类条件的
  `visibleSessions`，不会跳到筛选之外，也不创建新的会话分类。手机显示位置计数，
  桌面隐藏这组高频巡检控件。
- **恢复焦点指向“最后查看”，不是“最初打开”。** 用户可能在详情里连续切换多条；
  关闭后回到当前 Session 卡才能保持列表位置感。Session key 只写进页面元素的
  `data-*` 做本地焦点定位，不进入 URL、存储或新接口。
- **禁用当前按钮会让浏览器丢焦点。** 切到列表边界后，触发导航的按钮可能立即变为
  disabled；详情在 React 提交后的 effect 中把焦点转到仍可用的相邻按钮，避免焦点
  短暂落到 body、逃出模态。

## 2026-07-29 移动端 UI 第四轮取舍

- **底栏提示只复用现有状态，不发明移动端数据。** “待处理”徽标读取当前设备范围
  下既有 `SessionTab` 计数，设备圆点只表示已有设备筛选生效；全局概览仍不随设备
  筛选收窄。数量超过 99 时只显示 `99+`，辅助名称仍包含真实数量。
- **浏览器离线与网关错误是两层状态。** `online/offline` 事件负责立即停止 SSE、
  避免无意义刷新并提示保留上次内存快照；恢复联网后立即刷新并重建 SSE。它不证明
  Gateway 可达，在线后的请求错误仍走原有网关错误状态。Service Worker 继续没有
  fetch 缓存，刷新页面后不承诺离线数据。
- **手机横屏不能只用 CSS 宽度判断。** 844×390 一类横屏手机会越过 760px 竖屏
  断点，因此移动壳额外使用“宽度不超过 920px、高度不超过 480px、横屏”的组合；
  概览恢复四列以利用横向空间，导航与底部内容仍消费 safe-area。
- **实际系统安装继续是独立动作。** 本轮再次确认 manifest 无解析错误、
  installability error 为 0 且设置页显示“安装应用”，但没有点击确认，所以交付
  仍是可安装 PWA，而不是已写入当前机器应用列表。

## 2026-07-29 移动端 UI 第三轮取舍

- **连接健康在手机上也是核心信息。** 过去小于 520px 为了压缩标题直接隐藏
  `connection-pill`，会让用户无法区分实时、轮询和同步失败。现在标题改为两行网格，
  设置按钮仍在首行，连接状态占满第二行，不需要复制一套移动端状态组件。
- **安全区要覆盖独立窗口的整个钻取链。** 只有底栏避让底部不足以支持 PWA
  standalone；manifest 页面声明 `viewport-fit=cover` 后，主面板和全屏详情分别消费
  顶部/底部 inset，底部抽屉继续从安全区上方展开。
- **底部面板按真正模态处理。** 筛选和设置共享焦点圈定逻辑：初始焦点进入关闭按钮，
  Tab/Shift+Tab 循环，Escape 关闭并恢复触发点，同时锁定背景滚动。视觉动效只增强
  空间关系，`prefers-reduced-motion` 下完全停用。
- **可安装性与实际安装分开验收。** 普通 Chrome 的 DevTools 返回 manifest 无解析
  错误且 installability error 为 0，页面也收到 `beforeinstallprompt` 并显示安装
  按钮；本轮没有点击按钮或写入系统应用列表，因此只结论“具备安装条件”，不声称
  已完成系统安装。

## 2026-07-28 移动端 UI 第二轮取舍

- **设备页先展示“已观测”，不伪造“已安装/已登录”。** 当前 Gateway 的权威读模型
  只有绑定设备和 Session 元数据，没有每台设备的 Agent 安装或账号登录清单。因此
  设备卡只汇总 Session 中出现过的 Agent 类型以及全部、活动、等待会话数；后续若要
  展示安装/登录状态，必须先扩展 Runner 采集、隐私白名单和 API 契约。
- **固定导航只保留最高频路径。** 全部、活动、待处理保持一触即达，第四项改成设备
  入口；最近完成与历史进入完整筛选抽屉。所有入口仍写入同一 `SessionTab` 与设备
  筛选状态，避免桌面和移动语义漂移。
- **安装状态服从浏览器能力，不用 UA 猜测成功。** 只有收到 `beforeinstallprompt`
  才提供直接安装；standalone、安装提交、iOS 手动添加和不可用分别显示真实状态。
  安装动作不触发通知权限，Service Worker 自动注册也继续没有 fetch 缓存。
- **窄屏隐藏桌面控制面，但不减少功能。** 760px 以下使用列表标题旁的筛选入口和
  底部抽屉承载五类视图、设备选择、计数、重置与应用；桌面控制面保持原布局。真实
  38 条同步会话在 390×844 视口验证组合筛选、滚动锁定和横向边界。

## 2026-07-28 移动端 UI 第一版取舍

- **先做同一 PWA 的移动壳，不创建原生客户端目录。** 第一阶段的核心能力是只读
  监控和 Web Push，现有读接口、SSE、通知点击与详情模型都能直接复用；此时拆出
  React Native 或原生工程只会制造两套分类、鉴权和隐私白名单实现。需要可靠后台、
  商店分发或平台专属能力时再评估原生壳。
- **底部导航只放高频动作，完整分类仍留在控制面。** 第一版把全部、活动、待处理、
  完成和设置作为单手快捷入口；第二版根据设备入口优先级把完成移入完整筛选抽屉。
  底部导航调用同一个 `SessionTab`，不能另建移动端分类语义。
- **固定底栏必须和内容、安全区、全屏层级一起设计。** 面板底部预留导航高度与
  `env(safe-area-inset-bottom)`；设置操作栏也避让安全区；Session 详情的层级高于
  底栏，避免审批状态被导航遮挡。设置面板使用动态视口高度而不是传统 `100vh`，
  适应手机浏览器地址栏伸缩。
- **加载、错误和空状态共享桌面/移动实现。** 骨架屏避免第一次拉取时把“尚未加载”
  误显示为真实的 0；错误保留页面结构并提供重连；空筛选提供恢复入口。这些是产品
  状态，不应该在移动端重新复制一套分支。

## 2026-07-28 Web 监控信息层级取舍

- **首屏先回答全局规模和异常，不把设备筛选冒充全局状态。** 四张概览卡始终基于
  owner 的完整快照，设备筛选只收窄下方会话列表；这样用户切到单设备后仍能知道
  其他设备是否存在等待事项。控制面把“范围”和“视图”并列展示，明确两者都是
  查询维度，而不是互斥页面。
- **等待会话用颜色、文案和排序共同表达，不只依赖颜色。** 卡片左边界和暖色底用于
  快速扫视，同时保留“等待权限批准”等文字与状态徽标，降低色觉差异和低质量屏幕
  带来的识别风险。未知 Codex Thread 继续显示“未知”，不为了视觉完整伪造状态。
- **移动端详情是临时全屏钻取，桌面端才并列。** 监控列表需要保留足够宽度承载
  项目、Agent、设备和时间；窄屏硬塞双栏会让信息不可读，因此 920px 以下使用
  全屏详情并提供明确关闭入口，返回后保持原筛选和列表位置。
- **本轮只改变呈现，不扩张数据边界。** 概览和卡片完全复用已有设备/Session
  响应，不增加任务标题、消息内容、命令输出或路径字段；UI 视觉升级不能成为扩大
  上传白名单的理由。

## 2026-07-28 M4 自动化验收取舍

- **现场证据按层级关闭，不用一项通过代表整条链。** PostgreSQL 18.4 已让原先
  跳过的两项数据库用例变成真实通过；Codex CLI 0.144.2 只证明当前版本的一次性
  Thread 列表可采集；Chrome 的 `permission=granted` 与订阅 204 只证明订阅链，
  在系统没有留下活动通知时不能写成实际投递通过。
- **压力回归不设机器相关耗时门槛。** 12 设备/3000 Session 用例要钉死多 owner
  隔离、序列、重放和返回字段，不用一个在开发机上测得的毫秒数制造 CI 偶发失败。
  真正的吞吐、P95 和容量结论要在确定规格的 PostgreSQL 环境单独基准。
- **新版 Agent 输入宽松，平台输出严格。** Claude/Codex 本地输入允许未知字段，
  否则上游一加字段就会让整批监控失明；未知状态或 Hook 则必须降为
  `UNKNOWN + inferred`。进入 Outbox 和同步协议后继续严格白名单、拒绝未知字段。
- **断网验收分两层。** 当前自动化用磁盘 Outbox 与已释放回环端口证明“传输失败
  绝不清队列”，关闭并重开 SQLite 后仍按原序重放；后台线程也已覆盖真实回环端口
  先失败、端点恢复后自动 ACK 清零。真实 TLS 和长时间外部网络断开仍属环境验收。
- **内存压力不等于 PostgreSQL 压力。** 完整 HTTP 注册/验签/查询路径已覆盖，
  PostgreSQL 侧也以 4 条连接实际跑过同样的 12 设备/3000 Session 工作负载；
  它证明本机 PostgreSQL 18.4 上的事务、锁和隔离契约，不冒充生产规格容量基准。

## 2026-07-28 个人部署访问认证取舍

- **先提供服务端静态 Bearer 令牌，不在厂商未定时伪装成完整账号系统。** 当前产品
  已有单 owner 环境变量和个人监控部署路径；一个高熵令牌能关闭任意 `x-user-id`
  冒充风险，又不提前绑定 OAuth/OIDC 厂商。多用户登录、签发、轮换、撤销和审计仍
  明确留在账号系统范围，不能把本轮写成它们已经完成。
- **令牌只留在两个服务端进程。** Gateway 从环境读取并构造认证器后删除该环境项，
  认证器只保留 SHA-256 摘要；Web Route Handler 从服务端环境注入请求。浏览器
  localStorage、URL、Cookie 和前端配置都不携带令牌，浏览器自带的 Authorization
  也不能覆盖部署凭据。
- **开发身份必须双重显式。** `x-user-id` 只有设置开发认证开关时才生效，且该模式
  不能监听非回环地址。应用工厂在未注入认证器时也默认拒绝；协议测试必须显式注入
  开发认证器，真正的 `server.ts` 启动入口默认必须有访问令牌。
- **同源代理改为 Route Handler。** Next rewrites 无法安全注入服务端请求头，因此
  普通 JSON API 与 SSE 都由代码代理；只转发 accept/content-type，Cookie 和浏览器
  Authorization 一律丢弃。部署凭据不会因为前端输入或跨源直连进入浏览器。

## 2026-07-27 Service Worker 取舍

- **Service Worker 只做推送，仍然不做离线缓存。** 07-27 早些时候"PWA 第一步
  只做 manifest"的理由没变：实时监控面板缓存旧数据没有意义。现在引入 SW 是
  因为 Web Push 强制要求它，不是因为要离线——因此 sw.js 里没有 fetch 处理器，
  也就不存在缓存失效问题。
- **通知点击用 postMessage 传会话，不用 URL 参数。** 落回"标识不进 URL"的
  既有决策：会话 ID 和设备 ID 进了 URL 就会进历史记录和分享链接。代价是没有
  已打开窗口时只能打开首页而无法直接定位会话——这种情况下面板本来也要先拉
  数据，用户多点一次可以接受。
- **先问网关要密钥，再向用户要权限。** 通知权限只有一次机会，被拒绝就得用户
  自己去站点设置里改。所以 `enableNotifications` 先确认网关真的能发
  （`/v1/push/key` 有响应），再调 `requestPermission`。
- **登记失败就撤销刚建的订阅。** 否则浏览器侧留着一个网关不知道的订阅，用户
  看到的是"已开启"但永远收不到通知，且只能清站点数据才能复位。
- **通知标题在 sw.js 里本地维护。** SW 是纯 JS，拿不到 contracts 的类型约束，
  所以只映射它唯一会收到的两个等待状态并留兜底文案；把标题放进推送负载会让
  服务端持有 UI 文案，比这两行重复更糟。

## 2026-07-27 Web Push 取舍

- **自实现 RFC 8291 加密，不引 `web-push`。** 网关依赖至今只有 fastify 和
  postgres，刚清零的 npm audit 不想为一个能用 `node:crypto` 写完的功能重新打开
  依赖链。风险控制手段是 RFC 8291 §5 官方示例向量：固定 salt 与临时密钥后输出
  必须逐字节相等——实现写错不可能碰巧撞上那 200 个字符。另加一个随机往返用例
  证明每条消息的 salt 与临时密钥都是新的。
- **只有"进入等待"才通知。** 完成/失败/离开等待都不推送。面板是监控台不是
  信息流，什么都推等于训练用户忽略通知；PRD 里的痛点原话就是"等待输入或权限
  批准时用户可能无法及时发现"。将来要加"失败也提醒"应该做成用户开关，不是
  默认行为。
- **推送在请求路径之外发。** Runner 的 `sync push` 不该等 FCM 的往返，更不该
  因为推送失败收到一个会让它重试整批的错误码；因此入库成功就先回 200，通知
  异步发。每次等待状态投递只记录 `delivered / gone / failed` 聚合计数，不记录
  endpoint、owner、Session ID 或通知 payload，兼顾现场诊断与元数据边界。
- **404/410 立即删订阅。** 推送服务用这两个码表示订阅已失效；留着只会让以后
  每条通知都白打一次请求。其他失败（超时、5xx、429）保留订阅不删。
- **通知负载不比面板多一个字段。** 设备、Agent 类型、会话 ID、项目显示名、
  状态、等待原因、观察时间——都是面板列表已经显示的内容。负载虽然是端到端
  加密的（推送服务看不到明文），但"传输过的就可能泄漏"，字段策略不因加密放宽。
- **浏览器展示回执只留在页面内存。** `showNotification()` 成功后需要一个信号把
  “FCM 接受”与“Service Worker 已解密并提交展示”分开，但把回执写回 Gateway
  会新增遥测与持久化边界。当前只向已打开的同源面板发送无 Session/设备信息的
  时间戳，页面关闭即消失；它不声称 Windows 一定弹出了 Toast。
- **endpoint 强制 HTTPS。** 推送服务本来就是 HTTPS；强制它同时挡住"用订阅把
  网关指向内网明文地址"。残留敞口是 HTTPS 内网地址仍可注册——需要出站地址
  白名单或 DNS 解析校验才能彻底堵，留到正式认证一起做。
- **endpoint 是主键，换用户即改主。** 一个 endpoint 就是一个浏览器安装；同一
  浏览器换用户登录后订阅应该跟着走。开发期没有真实认证，这个语义等于"谁最后
  订阅就归谁"，正式认证后仍然成立。

## 2026-07-27 实时通道取舍

- **用 SSE 而不是架构文档写的 WebSocket。** 只读阶段数据流只有网关→面板一个
  方向，WebSocket 的双工能力用不上；更关键的是面板经同源 HTTP 代理访问网关，
  当前 Route Handler 不转发 upgrade 请求。改 WebSocket 需要另做带认证的 upgrade
  代理；等第一阶段结束真要做"手机端回复/批准"时再评估，那时双向价值足以覆盖
  额外复杂度。技术栈清单里的 WebSocket 保留给 Runner→Gateway 的 Device
  Gateway，不受此影响。
- **流只送"有变化"信号，不送会话数据。** 客户端收到信号后回读既有查询接口。
  这样字段策略只有一处实现，实时通道不可能偷偷多带字段；代价是每次变化多一个
  往返，对一个 5 秒轮询起家的面板完全不是问题。
- **面板用 fetch 读流，不用 EventSource。** EventSource 不能设请求头，而网关
  用 `x-user-id` 识别 owner，唯一替代是把用户标识塞进查询串——那正是面板一直
  避免的（进历史、进日志、进分享链接）。代价是自己实现帧解析与退避重连，约
  150 行且可单测。
- **轮询不删除，只降级。** 进程内 broker 在多实例部署下会漏推，标签页休眠、
  代理缓冲也会丢帧；连上流后 30 秒兜底轮询能在下一拍自愈，而删掉轮询会让这些
  情况变成"面板永远停在旧状态"。
- **每 owner 8 条流上限。** 一个面板一条流，8 条足够多开标签页；上限的意义是
  让卡死或恶意客户端不能把连接和心跳定时器无限堆在一个 owner 上。

## 2026-07-27 M3 Web 面板取舍

- **分类视图是过滤器，不是分区。** 五个 Tab 直接映射 ARCHITECTURE §4.4 的
  读视图清单，允许重叠：PERSISTED+FAILED 同时出现在"最近完成"和"历史"。
  强行分区会让"历史里那次失败"这类信息只能出现在一处，与双维状态模型冲突。
  等待中的会话在所有列表里置顶。
- **同源代理替代网关 CORS。** 当前 Next Route Handler 把 `/v1` 转发到网关并在
  服务端注入访问令牌；网关因此不必开放跨源，凭据也不进入浏览器。设置页保留
  "直连地址"入口并沿用 Runner 的出站策略（HTTPS 或回环 HTTP），但个人令牌部署
  必须保持同源，跨源直连仍不提前放开。
- **前端对 contracts 只 `import type`。** contracts 顶层引用 node:crypto，
  值导入会把它拖进浏览器 bundle。运行时需要的枚举标签在前端用
  `Record<Enum, string>` 本地维护，键完整性由编译器对合约类型强制，漂移会
  直接编译失败。
- **PWA 第一步只做 manifest。** 可安装（添加到主屏）已满足移动端诉求；
  service worker 离线缓存对实时监控面板没有意义，先不引入缓存失效复杂度。
  推送通知等原生能力按架构文档留到后续评估。
- **postcss/sharp 用 npm overrides 顶到修复版。** 三个高危 advisory 覆盖
  Next 全部现行版本（含 16.3 预览），npm audit 给出的"降级 next@9"不可行。
  Next 构建管线用的是自带打包的 postcss，node_modules 这份主要服务插件互
  操作；sharp 只被我们不使用的 next/image 优化用到，因此 override 越过
  Next 声明范围（8.4.31 精确钉死、^0.34.5）风险可控，dev 服务器与页面已
  实测正常。
- **时间线接口 limit 上限 500。** 这是面板轮询接口，不是审计导出接口；
  更长的历史属于后续"事件导出/分页"需求，先不给面板一个能拖垮网关的参数。
- **网关地址与用户标识存 localStorage，不进 URL。** 避免个人标识进入
  历史记录、日志和分享链接；损坏的存量配置静默回落默认值。

## 2026-07-27 全量代码审查后的取舍

- **同步事件携带合并后的状态，而不是原始观察。** ARCHITECTURE §6.2 规定
  `notLoaded` "保留最近状态"，但该保留此前只发生在本地快照表；事件流上传原始
  观察，服务端快照整体替换后云端会退化为 UNKNOWN，本地与云端展示分叉。改为在
  入队事务内先合并再落事件，云端 = 本地由构造保证。事件仍保留本次观察自身的
  `event_id` 与 `observed_at`（直接复用合并结果会在乱序观察时把上一事件的 ID
  带进新序列，被网关判为 event_conflict）。
- **注册持有证明在开发期就加，不等正式认证。** 绑定码仍是流程探针，但"公钥
  即可注册"让任何观察到批次的人都能抢注他人设备，这是协议缺口而不是认证缺口；
  签名输入固定为 `{binding_code, device_id, public_key}` 紧凑 JSON 声明序，
  与批次签名同一套跨语言规则。
- **重放已存批次仍然刷新 last_seen_at 是有意行为。** 一份验签通过的批次意味着
  该设备刚刚真实连过来；把"重复内容"与"设备活性"混为一谈才是错的。第三方拿到
  历史批次伪造在线需要先拿到批次本身，HTTPS 信道外不可得。
- **快照平手裁决存在毫秒/微秒精度差，接受不修。** 内存 store 用 `Date.parse`
  毫秒精度，PostgreSQL 用 timestamptz 微秒精度，亚毫秒差异的两事件可能选出
  不同的"当前快照"；两侧都有 sequence 终极平手线，实际影响限于展示层瞬时选择，
  统一精度的改造成本不值。
- **`run` 不强制 `--identity`，错配用警告兜底。** 强制会破坏纯本地诊断用法；
  改为 `sync push` 发现"0 批次可发但 Outbox 有事件"时提示事件归属另一设备 ID。
- **Codex `thread/closed` 映射 Presence=UNKNOWN。** closed 只说明连接不再
  跟踪该 thread，不证明任务停止；与 `notLoaded` 同样处理，置信度 Inferred。
- **`stopped` 且 pid 存活时 Presence=LIVE，修文档不修代码。** §5.1 对 LIVE 的
  定义就是"确认进程仍存活"；stopped 但窗口未关的会话不该被"历史"过滤吞掉。
- **Outbox 与快照表暂无保留策略，是已知敞口。** 长期本地-only 运行事件表无限
  增长；保留/清理需要产品级决策（离线多久算可弃、快照是否分层），列入
  SYNC_PROTOCOL 尚未实现清单，不在本轮拍板。
- **`sync verify` 的语义从"已知字段投影有效"收紧为"结构完全匹配"。** 此前
  向批次文件注入未声明字段仍报 valid——签名验证重建的是解析后的投影，注入值
  被静默丢弃；`deny_unknown_fields` 后该命令可以当作"这份文件未被改动"的
  本地判据（SyncAck 同步收紧，网关响应必须恰为四字段）。

## 2026-07-25 第一阶段 Runner 设计取舍

- **“历史”不作为活动状态。** 一个历史 Session 仍可能保留“最近一次执行失败”
  这样的活动结果；把两者压进同一个枚举会丢信息。因此使用 `Presence` 表示
  实时/持久化/未知，使用 `ActivityStatus` 表示工作、等待、完成等活动状态。
- **优先官方只读接口和 Hook，不扫描私有登录文件。** Claude 使用
  `agents --json` 与生命周期 Hook；Codex 使用 app-server 与 Hook。即使扫描本地
  transcript 能得到更多内容，也会扩大隐私面并绑定不稳定的内部格式，因此否决。
- **项目关联使用显示名加 HMAC 指纹。** 只传 basename 无法区分多块磁盘或不同父目录
  下的同名项目；上传绝对路径又会泄露用户名与目录结构。设备密钥派生的 HMAC 指纹在
  同一设备内稳定，同时不暴露原路径。
- **Codex `notLoaded` 不等于历史。** 它只表示 Thread 当前未加载到该 app-server
  进程，不能据此证明任务停止或仅剩持久化记录，所以映射为未知 Presence，并由快照
  合并逻辑保留最近可信活动状态。
- **真实 CLI 验证放在实现与 Fixture 验证之后。** Runner 的开发和回归测试不应依赖
  开发机是否安装 Claude CLI，或 WindowsApps 是否允许当前 Shell 执行 Codex。

## 2026-07-25 持续采集调度取舍

- **每个 Adapter 独立退避。** Claude CLI 不可用时不能拖慢 Codex，反过来也一样；
  因此失败次数和下次尝试时间按 Agent 分开保存，而不是整个 Runner 共用一个退避器。
- **错误诊断保存分类，不保存原文。** 进程启动错误可能包含用户名、安装路径或系统
  环境细节。云端和本地健康表只需要知道 `permission_denied`、
  `executable_not_found` 等稳定分类，原始错误不进入持久化。
- **轮询事件按快照变化去重。** `observed_at` 和随机 `event_id` 每次都会变化，不能用于
  判断 Session 是否真的变化；比较时忽略这两个传输字段，保留状态、项目、来源、
  置信度和 Agent 提供的活动时间。
- **Codex app-server 在连续轮询间复用。** 每轮重新握手成本高且会制造短命进程；
  Runner 保持一个 stdio app-server，协议失败后丢弃并在下一次退避到期时重建。
- **超时覆盖进程树和读取线程的完整生命周期。** 单纯在外层计时不能解除被后代进程
  持有的 stdout 管道；实现必须在截止时间到达时终止完整进程树，等待直接子进程退出，
  再回收读取线程。Claude 静默命令和 Codex 静默握手均有故障注入测试。

## 2026-07-25 Codex 被动通知取舍

- **不为获取通知而启动或恢复用户 Thread。** Codex 官方只保证当前 app-server
  连接启动或恢复 Thread 后的 Turn/Item 通知，但 `thread/start`、`thread/resume`
  会让监控端参与 Session 生命周期，超出第一阶段只读边界。因此 Runner 只处理连接
  自然收到的通知，并以 `thread/list`、`thread/loaded/list` 轮询兜底。
- **在协议入口退出内容型通知。** 初始化的 `optOutNotificationMethods` 覆盖消息、
  推理、计划、Diff、命令输出和完整 Item 等载荷；审批、用户输入和状态通知仍可用于
  元数据判断，进入 Outbox 前继续经过字段白名单。
- **真实覆盖率是待验证事实，不是实现假设。** 当前开发机的 Codex WindowsApps
  二进制不可执行，Fixture 已验证解析、覆盖优先级和隐私边界，但跨客户端 Thread
  是否向独立 app-server 广播全部状态通知要留到真实 CLI 验证。

## 2026-07-25 设备身份与同步契约取舍

- **使用非对称设备身份，不让云端保存共享私密材料。** Ed25519 私钥只保留在 Runner，
  云端绑定公钥即可验证批次；设备 ID 由公钥摘要派生，避免独立随机 ID 与密钥错配。
- **设备私钥同时派生项目指纹密钥。** 传入 `--identity` 时不再要求额外环境变量，
  目录 HMAC 与设备身份自然保持一致。旧的 `--device-id` 加环境密钥方式暂时保留，
  方便 Fixture 和迁移。
- **确认必须绑定本次实际发送范围。** 仅凭服务端返回的最大序列直接删除会让错误或
  恶意确认越过当前批次，丢失尚未发送事件；因此确认同时匹配版本、设备、批次 ID，
  且 `accepted_through` 必须位于批次首末序列之间。
- **先固定本地协议边界，再接真实网络。** 当前实现只负责签名、验证、重放素材和确认
  清理，不自行选择 WebSocket 库、服务地址或绑定流程；这些要与 Device Gateway
  一起实现，避免诊断命令提前固化生产鉴权。
- **版本 1 签名依赖明确的紧凑 JSON 字段顺序。** Rust 端签名和验证使用同一类型，
  Map 字段按键排序。当前已有 TypeScript 生成、Rust 验证的固定向量；未来任何语言
  无法稳定复现时，协议升级到标准 JSON Canonicalization Scheme，不能静默改变版本
  1 字节序列。

## 2026-07-25 Gateway 第一阶段取舍

- **存储接口先于 PostgreSQL 实现。** `GatewayStore` 固定注册、批次写入、设备查询和
  Session 查询语义，内存实现用于验证原子性、幂等和冲突规则。它不冒充持久化方案；
  PostgreSQL 版本必须以同一契约通过测试后才能替换。
- **一次性绑定码是流程探针，不是认证系统。** 此阶段代码只证明绑定码绑定单台设备、
  重试幂等和公钥不可替换，当时由环境变量提供且不持久化；该阶段性边界已由
  2026-07-28 的受认证签发、过期、持久化与软撤销设计取代。
- **HTTP 先验证请求/响应，WebSocket 后承载同一消息。** 签名、白名单、幂等和确认
  与传输无关，先用 Fastify HTTP 和 `inject` 完成确定性测试；心跳和低延迟推送接入
  时复用相同 Contracts，不另造事件格式。
- **开发用户头明确隔离。** `x-user-id` 只让只读查询测试具备租户边界，不提供任何
  安全承诺；现已由个人部署 Bearer 认证替代，只在显式开发开关和回环监听下保留。
- **任务标题默认不进入云端。** Codex `name/title` 和 Claude Agent `name` 可能来自
  用户任务文本，不能因为字段叫“名称”就当成无害元数据。未实现明确 opt-in 前，
  Adapter 不保存、同步线协议也不接受 Session `display_name`。

## 2026-07-25 Runner 出站同步取舍

- **后台同步与采集分线程、分连接。** `sync push` 的有界批次与 ACK 语义保持不变；
  常驻 `run` 用独立 SQLite 连接排空 Outbox，网络等待和退避不会阻塞 Adapter。
  容量为 1 的唤醒通道只表达“有新事件”，离线期间重复采集不会堆积通知。
- **失败退避不能被新事件绕过。** 同步成功时新事件可立即唤醒；一旦网络失败，退避
  窗口内的唤醒只合并不抢跑，避免离线时每次采集都重置连接风暴。启动时先尝试排空，
  因此进程重启不需要手工执行 `sync push`。
- **暂不持久化在途 batch_id。** 请求响应前进程退出会让下次重签同一组事件；服务端
  按 event_id 幂等，ACK 仍只能删除实际发送范围。在途批次持久化留给需要严格审计
  单次传输身份的阶段，不阻塞当前可靠恢复。
- **ACK 是删除权限，不是普通成功提示。** Runner 在本地重新验证原批次签名，并校验
  版本、设备、批次 ID 和序列范围后才删除 Outbox。服务端返回 2xx 但正文无效时与
  传输失败等价，不能清队列。
- **远程明文传输默认拒绝。** 生产地址只接受 HTTPS；HTTP 例外严格限制在回环主机，
  使本地真实 Gateway 验证无需伪造证书，同时避免一个误配置把元数据和绑定码发送到
  局域网或公网明文端点。
- **错误输出只保留稳定分类。** HTTP 状态码可用于诊断，但服务端响应正文和底层连接
  错误可能包含部署路径、代理信息或其他敏感细节，不进入持久化状态，也不直接回显。

## 2026-07-25 PostgreSQL 持久化取舍

- **Store 契约统一异步，不在 PostgreSQL 外包同步假象。** Fastify 路由统一等待
  `GatewayStore`；内存实现也返回 Promise，因此协议测试和持久化实现不会形成两套
  调用语义。
- **按设备串行、跨设备并行。** 批次事务先 `FOR UPDATE` 锁定目标设备行，同一设备的
  序列判断不会并发穿透，不同设备又不需要争抢全局锁。事件 ID 和设备序列唯一约束
  继续作为数据库最终防线。
- **事件流不可变，快照可合并。** 完整白名单 `SyncEvent` 以 JSONB 保存用于审计和
  重放，Session 表只保存每个设备/Agent/Session 的当前胜出事件，并额外提取状态列
  支持查询；不为便利新增 Prompt、代码或完整路径字段。
- **历史迁移不可修改。** 迁移版本之外记录 SHA-256；已应用文件发生变化时启动失败，
  后续结构调整必须新增迁移。事务级 advisory lock 只保护迁移，不把正常批次写入
  全局串行化。
- **绑定码暂不伪装成持久认证。** 这是首版 PostgreSQL Store 的阶段性边界，已由
  2026-07-28 的设备生命周期设计取代。

## 2026-07-28 设备生命周期取舍

- **原码只返回一次，Store 只保存摘要。** 绑定码使用 32 字节随机数生成，默认
  10 分钟有效；API 返回原码后仅把 SHA-256 摘要交给 Store，数据库泄露不会直接
  暴露仍有效的绑定凭据。
- **单次领取必须在存储层原子化。** PostgreSQL 对绑定码行执行 `FOR UPDATE`，同一
  设备重试返回既有登记，另一设备并发领取返回 `binding_code_used`。内存实现也在
  第一个异步写入前预占设备 ID，并在登记失败时释放。
- **撤销采用软删除。** 用户撤销设备后保留不可变事件和 Session 历史，设备列表明确
  显示「已撤销」，并拒绝重新登记与后续同步。这样不会为了阻断凭据而破坏监控审计链。
- **保留已领取码，清理过期未领取码。** 已领取记录支持网络响应丢失后的同设备幂等
  重试；未领取且过期的记录在下一次签发时清理，避免无效签发记录无界增长。密钥轮换、
  恢复绑定和完整审计日志仍需后续账号体系。

## 2026-07-28 私有 CA 与离线可观测性取舍

- **允许增加信任根，不允许关闭验证。** 私有部署可向 Runner 提供一个 CA 根证书
  PEM，但证书链、主机名和有效期仍由 rustls 严格验证。仓库不提供
  `danger_accept_invalid_certs` 一类开关，避免绑定码和会话元数据在“临时调试”中
  悄然暴露给中间人。
- **私有根只作用于 Gateway 客户端。** 配置私有 CA 时替换该 Runner Gateway
  连接的 WebPKI 根集合，不修改系统证书库，也不影响 Agent CLI 自己的网络行为。
- **失败报告必须证明积压仍在。** 长时间离线时只报告错误码不足以区分“仍有待发送
  数据”和“队列已经异常丢失”；后台同步每次失败后从磁盘 Outbox 读取
  `pending_events`。统计读取本身失败时才省略该字段，避免用虚假的零掩盖数据库故障。

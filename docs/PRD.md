# AgentHub 产品需求文档 (PRD)

更新：2026-09-08。

## 顶层产品定位（核心宪法）

**AgentHub = 多种本地 AI Agent 的统一远程控制入口。**

它只专注做三件事：
1. **发现**：发现本机正在运行的 Codex / Claude 等官方 Agent；
2. **接管**：接管它们现有的运行中 Session（以及历史上下文）；
3. **暴露**：把这些 Session 安全暴露给手机端和 Web 端继续使用。

### 核心三大原则（三不原则）
- **不替代官方 Agent**：用户依然使用官方 Codex、Claude 等工具，我们不做第四方套壳 Agent。
- **不自己再造 Agent**：执行、上下文与推理完全依托官方 Agent 的本地引擎，AgentHub 不自建独立 Prompt/Agent 决策循环。
- **不改变用户本地使用习惯**：本地在 Terminal、VS Code 或官方桌面端怎么用，就怎么用。

### 唯一需求判断标准
> **“这个功能是不是在帮助用户‘远程继续使用本机已经运行的 Agent’？”**
> **如果答案不是，坚决不做。**

本地在电脑前照常用 Codex、Claude；**一旦离开电脑，用户统一从 AgentHub 手机端或 Web 端继续看、继续聊、处理审批、停止任务、查看结果**。

## 用户核心旅程与使用场景

1. **场景 1：电脑前工作（原生习惯不打扰）**
   - 用户在本地打开终端运行 `codex` 或 `claude`，正常提交任务与交互。
   - AgentHub 桌面端/Runner 作为安静的后台守护进程，自动发现运行中的会话及工作区。
2. **场景 2：离开工位（远程无缝接管）**
   - 用户出门、开会或离开电脑，打开手机端（Android）或 Web 端。
   - 看到电脑上当前运行中的同一个会话：正在输出的代码、当前的耗时、实时的思考流。
3. **场景 3：移动端审批与交互**
   - 官方 Agent 在电脑端触发了敏感命令执行审批（Tool/Shell Approval）：手机端立刻收到审批卡片，点击“允许”，电脑端立刻继续执行。
   - 发现 Agent 方向走偏：手机端点击“停止任务”，电脑端瞬间触发中断。
   - 想要追加需求：手机端直接打字发送，电脑端原生 Agent 继续接续同一个 Session。
4. **场景 4：回工位无缝继续**
   - 用户坐回电脑前，终端或桌面端的原生会话状态与手机端完全一致，零摩擦。

## 功能分类与范围控制（做什么 vs 不做什么）

| 模块 | 必须做（帮助远程接管） | 坚决不做（偏离远程入口） |
| --- | --- | --- |
| **发现层** | 自动发现本机 running 中的 Codex / Claude 会话与工作区 | 强制用户在 AgentHub 里从零配置环境与安装 CLI |
| **接管层** | 接入当前会话、捕获上下文/实时流、注入 Prompt、回传审批、发送中断 | 自造 Prompt 模板库、自建 Agent 决策大脑或自定义工作流 |
| **通道层** | 电脑出站长连接到 Gateway、断线重连补帧、加密验签、低延迟流式 | 要求电脑开放公网端口、复杂的内网穿透端口映射 |
| **端侧体验** | 手机端与 Web 端：极简流畅的实时对话、工具时间线、审批弹窗、急停按钮 | 臃肿的本地多合一开发 IDE、复杂的代码编辑器/项目工程管理 |

## 三种接入语义与状态模型

| 操作 | 含义 | 成功条件 |
| --- | --- | --- |
| 发现 discover | 发现原生历史或进程元数据 | 有来源证据；只读，不代表可控制 |
| 恢复 resume | 使用同 Provider 的原生 ID 恢复上下文 | 原生协议返回该 ID，Runner 建立控制通道 |
| 连接 attach | 接入已经运行的会话 | 存在可验证的原生控制端点与所有权，且完成订阅 |

由 Runner 创建或恢复并持有控制通道的会话为 managed；外部发现但没有控制通道的会话为 discovered。服务端已有历史但 Runner 不可达时仍可查看，控制不可用。扫描文件、发现 PID、读取历史均不构成 attach。不能对未知外部进程自动执行 resume，以免形成两个并行执行者。

## 产品边界

- Workspace-first：设备内工作区是主要组织单位，工作区下可以有多个不同 Provider 的会话；Provider 是筛选条件，不是默认首页分区。
- hub_session_id 是稳定包装 ID；provider_session_id 来源于 Provider，两者均不能因换端或重连改变。跨 Provider 继续属于新会话，不能伪装为恢复。
- 执行状态、Runner 连通性、会话控制通道、客户端在线状态独立。
- 已接入远程控制的会话同步正文、工具请求/结果、审批与原始协议事件，服务端持久化供回放。旧只读扫描保持元数据范围，不能静默批量上传所有原生历史。
- 开启远程会话时清楚说明内容会同步到用户的 Hub；历史全文导入由用户明确选择。
- Provider 登录由原生 Agent 完成。新控制链路不读取/缓存/刷新 Provider 凭据，不把旧凭据管理接到新链路。
- 运行时权限属于会话。不能把不支持的权限、Slash 或模型配置显示为已生效。
- 同工作区不同 Session 允许并行并提示冲突；同一原生 Session 不允许被多个 Host 未协调地重复执行。
- 多端命令须有稳定 client_cmd_id；重复请求返回同一结果。提交成功、Provider 接受、执行完成是不同状态。
- 断线不自动重发已经可能执行过但结果未知的修改命令。未知结果先对齐，无法确定时显示需处理。
- 原生 Remote 私有隧道、任意进程无损接管、全 Provider 功能完全相同、固定 60fps/绝对零丢包都不是未经验证的承诺。

## 验收标准

一个 Provider 只有全部通过才算远程可用：真实 CLI 创建 → 连续两轮保持原生 ID → 两个客户端查看同一会话 → 流式正文与工具事件 → 原生审批只执行一次 → 中断由原生事件确认 → 客户端离线期间继续 → 断线重放无重复正文 → 服务重启历史保留 → Runner 重启后准确标记控制丢失并可显式恢复。

必须覆盖跨账户拒绝访问、设备撤销、重复命令、乱序/重复帧、缓存溢出和进程退出。Fixture/回环测试、真实 CLI、真机和生产验收分别记证据。

首个实现切片为 Codex app-server。Claude 在官方支持的认证与协议边界内接入；Antigravity/Grok 在真实能力证据建立前仅保留发现与历史查看。实施顺序和完成状态见 [文档索引](README.md)。
